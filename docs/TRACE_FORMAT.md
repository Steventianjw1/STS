# Trace format (`sts2-trace-1`)

Each `step` or `play-combat` run creates one session directory:

```
traces/<session_id>/
  manifest.json     session metadata (rewritten atomically at start and at end)
  decisions.jsonl   append-only records, one JSON object per line
  debug_raw.jsonl   raw API responses (only when record_raw = true) — NOT training data
```

`session_id` has the form `YYYYMMDDTHHMMSSZ-<6 hex>`, in UTC.

Every line is flushed and `fsync`ed as soon as it is written. If the process crashes, every earlier
line is preserved. The manifest's `ended_at` and `outcome` stay `null` until the session closes
cleanly, so a `null` there means the session crashed or was killed.

## Provenance

This data is generated by a heuristic agent. **It is not expert or human play.** The labels:

- `manifest.provenance` = `{"data_source": "agent_generated", "behavior": "heuristic_baseline_policy", "is_expert_demonstration": false, ...}`
- Every `decision` record carries `"provenance": "agent_generated_heuristic"`.

## manifest.json

| field | meaning |
|---|---|
| `trace_format` | `sts2-trace-1` |
| `session_id`, `run_id` | `run_id` comes from `/api/v1/compendium` `current_run.run_id` when the mod build has that endpoint, otherwise `null`. The seed is never recorded. |
| `command` | `step` or `play-combat` |
| `started_at`, `ended_at` | UTC ISO-8601 timestamps |
| `agent_version`, `observation_schema`, `policy` | versions needed to interpret and replay the data |
| `game_build` | Declared by you in the config. The API does not report it. `null` = unknown. |
| `mod_version` | Parsed from the mod's `GET /` greeting |
| `mod_source_commit_adapter_written_against` | The STS2MCP commit the adapter was written against |
| `config` | The effective config (limits, timeouts). Local paths are removed. |
| `outcome` | The session summary (`stop_reason`, `combat_result`, counts), or `null` if the session did not close |
| `counts` | The number of decision, outcome and error records |

## decisions.jsonl record types

Every record has `type`, `session_id`, `ts` (UTC) and `mono` (a monotonic clock in seconds, for
durations only).

### `decision` — what the policy saw and chose (written BEFORE the action is sent)

```jsonc
{
  "type": "decision", "seq": 3, "provenance": "agent_generated_heuristic",
  "input": {
    "observation": { /* normalized observation, schema sts2-obs-1, includes "fingerprint" */ },
    "candidates":  [ /* exactly the candidate actions given to the policy */ ]
  },
  "excluded_cards": [ {"index": 4, "name": "...", "reason": "unsupported effect text", "unsupported_effects": ["Draw 1 card"]} ],
  "decision": {
    "action_id": "play:0:STRIKE_IRONCLAD@101",
    "payload": {"action": "play_card", "card_index": 0, "target": "101"},
    "policy": {"name": "baseline-heuristic", "version": "1.0.0"},
    "rule": "lethal|prevent_damage|block|damage|end_turn",
    "reason": "Selected Strike because its verified damage (6) defeats every remaining enemy.",
    "scores": { /* the numbers the rule used */ }
  }
}
```

A `decision` record holds **no** information from after the decision was made. A training loader that
reads only `decision` records cannot see the future.

### `outcome` — what happened (written after resolution, same `seq`)

```jsonc
{
  "type": "outcome", "seq": 3,
  "verdict": "resolved",
  "response": {"accepted": true, "http_status": 200, "body": {"status": "ok", "message": "..."}, "elapsed_s": 0.02},
  "timing": {"send_s": 0.02, "resolution_s": 0.61},
  "observation_after": { /* normalized observation once the game settled */ },
  "detail": ""
}
```

Verdicts:

| verdict | meaning |
|---|---|
| `resolved` | The action was accepted, the state changed, and the state settled into a stable ready state |
| `resolved_screen_changed` | The action was accepted and the combat ended or a non-combat screen appeared |
| `stale_not_sent` | The state changed between the decision and the pre-send validation, so nothing was sent |
| `rejected` | The mod answered `status: error`. The action is blocked for that exact state. |
| `no_visible_change` / `timeout_after_change` | The action was accepted but did not settle. The session stops. |
| `ambiguous_inferred_executed` | The request timed out or failed, but the state changed afterwards, so it is treated as executed. It is never resent. |
| `ambiguous_unresolved` | The request timed out and the state did not change. The session stops without resending. |
| `not_delivered`, `not_sent_validation_read_failed` | Nothing was sent |
| `interrupted_during_send` | Ctrl+C was pressed while a request was in flight. The outcome is unknown. |

### Other records

- `event`: `session_start`, or `blocked_candidates` (`data.seq` and `data.action_ids` list candidates
  removed because the same state had already rejected them; replay uses this).
- `error`: for example `ambiguous_action_response`, `unexpected_exception`.
- `session_end`: `outcome` is the final summary.

## Observation schema (`sts2-obs-1`)

Built by `src/sts_agent/observation.py` from an explicit allowlist. `null` always means **unknown**,
never zero.

- `phase`: `combat_ready`, `combat_busy`, `combat_hand_select`, `combat_ended`,
  `post_combat_screen`, `game_over`, `menu`, `unsupported_overlay` or `unknown`.
  `ready_for_action` is true only for `combat_ready`.
- `run`: `character`, `ascension`, `difficulty` (`A<n>`), `act`, `floor`.
- `combat`: `round` (the turn number), `turn_side`, `is_play_phase`.
- `player`: `hp`, `max_hp`, `block`, `energy`, `max_energy`, `gold`, `statuses[]` (`id`, `name`,
  `amount`, `type`, `description`).
- `hand[]`: `index`, `instance_key` (positional `id#n`; the mod exposes no instance id), `id`,
  `name`, `type`, `cost` (`null` for X or unknown), `cost_is_x`, `description` (the live rendered
  text), `target_type`, `can_play`, `unplayable_reason`, `is_upgraded`, `keywords`, and `effects`
  (parsed from the description: `damage_per_hit`, `hits`, `block`, `applies`, `unsupported[]`,
  `fully_supported`).
- `piles`: `draw_count`, `discard_count`, `exhaust_count`; `draw_composition` (name → count, **no
  order**); `discard[]` and `exhaust[]` (card names).
- `enemies[]`: `combat_id` (stable, used as the target), `entity_id` (renumbered by the mod when an
  enemy dies), `name`, `hp`, `max_hp`, `block`, `statuses[]`, and `intents[]` (`type`, `label`,
  `title`, `description`, `is_attack`, `damage_per_hit`, `hits`, `total_damage`). Also
  `has_attack_intent` and `incoming_damage` (`null` when the attack size is unknown).
- `relics[]`, `potions[]` (visible only; never used automatically), `max_potion_slots`.
- `screen`: a small descriptor for selection prompts, overlays and messages.
- `fingerprint`: a sha256 prefix over the rest of the observation. Candidates are bound to it.

The observation never contains: draw order, RNG state or seed, map lookahead, unrevealed rewards,
profile or account data, or machine information.

## Replaying

```
sts-agent replay traces\<session_id>          # whole session
sts-agent replay traces\<session_id> -v       # show every decision
sts-agent replay saved_observation.json       # one observation saved with `observe --save`
```

For each `decision` record, replay does three things:

1. It recomputes the fingerprint, which detects edited or corrupted inputs.
2. It rebuilds the candidates from the recorded observation and compares them with the recorded
   list. This checks that the candidate builder is deterministic.
3. It re-runs the policy on the recorded candidates and compares the action and rule.

Replay never contacts the game and does not simulate it.

## LLM decision traces (`sts2-trace-2`)

`step`, `play-combat` and `play-run` write this format under the default `llm` policy. The layout
is the same as above: `manifest.json`, `decisions.jsonl`, and optionally `debug_raw.jsonl`.
Baseline sessions still write `sts2-trace-1`, and their replay is unchanged.

### Manifest additions

- `trace_format`: `sts2-trace-2`.
- `provenance`: one of the following.
  - LLM runs: `{"data_source": "agent_generated", "behavior": "llm_policy", "is_expert_demonstration": false, "facts_source": "observed" | "synthetic", "live_validated": false}`.
  - Scripted-model runs: `{"data_source": "synthetic", "behavior": "scripted_model_replies", "is_llm_reasoning": false, ...}`.
- `model`: provider identity (`provider`, `model`, `max_output_tokens`, `timeout_s`,
  `sdk_retries`, `scripted`). It never contains credentials.
- `decision_prompt_version`, `run_id_source` (`mod_compendium` or `session_scoped`),
  `facts_source`, `capabilities_mod_revision`.
- `model_usage`: calls, input and output tokens, budget limits, and an estimated cost only when
  prices are configured.

### Record types

| type | when | contents |
|---|---|---|
| `llm_decision` | Before any action is sent. | `seq`; `provenance` (`llm_generated`, `llm_generated_synthetic_input` or `synthetic_scripted_model`); `policy`; `prompt_version`; `model`; `frame` (full `DecisionFrame` record, including `frame_id`, facts, candidates, private `bindings`, limitations, assessment, previous turn intent and history); `choice` (`action_id`, `reason`, `turn_intent`, or `null`); `attempts` (response text up to 8 KiB, validation error, provider call record with usage/stop reason/latency); `error_kind`; `diagnostic`; `history_dropped`. |
| `outcome` | After resolution (same `seq`). | `verdict`, the game `response`, `timing.since_send_s`, `observation_after` (screen kind, fingerprint, facts), `detail`. |
| `strategic_update` | When the coordinator asked the planner. | `revision`, `snapshot_id`, `change_reasons`, `status`, `model_called`, `diagnostic`, the `assessment` envelope, `applies_to_current_facts`, and the provider call record. |
| `event` | Session milestones. | `session_start`; `combat_finished` with observed HP change, turns, and potions used by the agent. |
| `error` | Problems. | For example `ambiguous_action_response`, `strategic_snapshot_invalid`, `unexpected_exception`. |
| `session_end` | Session closed. | The summary. |

New verdicts are `accepted_unobservable` (a card-grid toggle the API cannot show),
`not_sent_deadline`, and `not_sent_validation_read_failed`. They are added to the verdicts listed
earlier.

The trace stores no hidden reasoning transcripts, only the contracted `reason` and `turn_intent`.

Relevant frames may also contain optional `decision_support`: the cached Spire
Codex expert cohort, filters, per-option counts/rates, contributor counts and
availability/cache provenance. This is external observational evidence, separate
from game facts. It participates in the frame hash and is replayed from the
record without a network request. Frames without this field retain their
original hashes. See [EXPERT_STATS.md](EXPERT_STATS.md).

### Replay of LLM traces: recorded-decision validation

`sts-agent replay traces\<session_id>` detects `llm_decision` records and **does not call any
model**. For each record it does three things:

1. It rebuilds the `DecisionFrame` from the record and checks that `frame_id` matches its content.
   This detects edited facts, candidates or bindings.
2. It checks that the recorded action was offered in that frame.
3. It re-parses the recorded response text and confirms that it validates to the recorded choice.

This validates what was recorded. **It is not reproduction of the LLM by resampling.**
